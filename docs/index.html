OptimFoundation
開發分層與開發形式

一個 solver-agnostic 的混合整數規劃（MIP）建模框架。把「定義問題」與「呼叫求解器」徹底分離：上層只描述變數、參數、限制式與目標式，下層負責對接 CPLEX / Gurobi。本頁依任務層級（從應用開發到核心底層）拆解，並列出框架支援的各種開發形式。

核心 OptimFoundation.Core 求解器 Cplex / Gurobi / Solver 資料 Csv / Db.Oracle 建模 Generators（宣告式） 研究 Experiments / Tuning

01 三層架構

上層依賴下層，下層不知道上層存在。Solver 可替換、Core 永不需為了某個問題而修改。

Project Layer問題定義者
你的最佳化問題（如 RosteringProblem）

Dataload、Parameter_*、Variable_*、Constraint_*、ObjectiveFunction、組裝與執行入口。

▲ 依賴 ▲
Solver Layer求解器實作
OptimFoundation.Cplex / .Gurobi / .Solver

各自一個 OptEngine : EngineBase<TModel,TVar,TExpr,TConstr> + 對應 ISolverConfig。封裝原生 solver interop。

▲ 依賴 ▲
Core Layer抽象合約
OptimFoundation.Core

ModelElementBase、VariableBuilder、EngineBase（Pool API / VariableSet）、求解器合約介面、Experiments、Infrastructure。solver 無關。

旁掛模組：Generators（編譯期生成建模樣板）、Csv / Db.Oracle（資料載入）橫跨各層，作為工具不參與主依賴鏈。

02 任務層級：從應用開發到核心底層

同一個框架，四種不同身分的開發者。愈上層門檻愈低（只寫問題），愈下層愈接近求解器與抽象合約。

L01建模者 · Modeler Project Layer / 應用最上層
把一個現實問題寫成模型：定義決策變數、參數、限制式、目標式與資料。不需碰任何 solver 細節。絕大多數開發都停在這一層。
做什麼Variable / Parameter / Constraint / Objective / Dataload
用到的型別VariableBase · ParameterBase · ConstraintBase · Pool API
會動的檔案Data/ · VariablesClass/ · Constraints/
標準建模宣告式建模軟性限制式資料載入
L02整合者 · Integrator 組裝管線 / 求解設定
把變數、限制式、目標式組裝成可執行的求解管線，調整 solver 參數，輸出結果，並做批次實驗與調參。負責「把模型跑起來、跑得好」。
做什麼組裝 pipeline · 設定 Config · 輸出 · 實驗
用到的型別OptModel · CplexConfig · Experiment / Trial
會動的檔案Program.cs · BuildModel.cs · 入口
OptModel 管線實驗與調參切換 Solver
L03求解工程師 · Solver Engineer 演算法 / 進階求解
需要存取 dual、固定變數界限、自訂求解流程，或實作分解演算法（Benders）、跨執行緒限制式。透過繼承 OptEngine 擴充行為。
做什麼繼承 OptEngine · Dual · Benders · Thread 限制式
用到的型別Model · IRange · ReadVar · SetVarLB/UB · MergeModel
會動的檔案自訂 MyEngine : OptEngine
繼承 OptEngineBenders 分解多 Solver
L04框架維護者 · Framework Maintainer Core / 底層
維護抽象合約與共用機制，或為框架新增一個求解器後端。動的是 Core 與 Solver adapter，影響所有上層。
做什麼新增 Solver · 改 EngineBase 合約 · Generators · 介面

03 支援的開發形式

框架不綁定單一寫法。從零樣板的宣告式建模、到無繼承的組裝管線、到分解演算法與多 solver，以下十種形式可依需求混用。每張卡片標註所屬任務層級。

FORM 01 · L01 建模
標準建模（Pool API · 命令式）
框架的基本形式：變數/參數/限制式都是「零建構子」class，限制式用 AddLHS / AddRHS 把左右兩側丟進 Pool，再 Create* 送出。
// 變數：只宣告 properties，不寫建構子
public class VariableB_ShiftAssign : VariableBase {
    public DateTime Date { get; set; }
    public string Employee { get; set; }
    public string Group { get; set; }
}

// 限制式：每人每天恰排一班  Σ_g X = 1
Data.Group.ForEach(g =>
    Engine.AddLHS(1, new VariableB_ShiftAssign{ Date=d, Employee=e, Group=g }));
Engine.AddRHS(1);
Engine.CreateEqual($"OneGroup@{d:yyyy_MM_dd}@{e}");
BuildBVs/IVs/CVsAddLHSAddRHSCreateEqual
FORM 02 · L01 建模
宣告式建模（Source Generator）
用 [OptVar] / [OptParam] 標記，AutoSetsGenerator 在編譯期把 set 屬性、QTY、建構子補齊。零樣板，宣告即模型。
using OptimFoundation.Modeling;

// 一行宣告 → 編譯期生成完整 class；型別由類別名前綴 VariableB_ 決定
[OptVar("Date:DateTime", "Employee", "Group")]
public partial class VariableB_ShiftAssign { }

// 參數一律生成 QTY 值欄位，且 QTY 必為最後一個資料屬性
[OptParam("Date:DateTime", "Group")]
public partial class Parameter_ShiftDemand { }
OptimFoundation.Generators[OptVar][OptParam]
FORM 03 · L02 整合
OptModel 組裝管線（Composition）
fluent registry：用 delegate 註冊變數 / 模型 / 求解後處理，Execute() 在對的時機叫起來。對具體 class 零依賴、不需繼承。
using var m = new OptModel("Rostering")
    .UseConfig(() => new CplexConfig{ timeLimit=100, epGap=0.03 })
    .AddVariables(e => e.BuildBVs<VariableB_ShiftAssign>(d.Date,d.Emp,d.Grp))
    .AddModel(e => new ObjectiveFunction(d,e).Build())
    .AddModel(e => new Constraint_OneGroup(d,e).Build())
    .OnSolved(e => d.WriteToCSV(e));
m.Execute();
UseConfigAddVariablesAddModelOnSolvedExecute
FORM 04 · L03 求解
繼承 OptEngine（進階擴充）
需要 dual、固定變數、保存 IRange 供後續取值時，繼承 OptEngine 取得 protected 的 Model / ReadVar / AddGE 等。
public class SubProblemEngine : OptEngine {
    public SubProblemEngine(CplexConfig c) : base(c) { }

    public void Build(List<string> dests, Dictionary<string,double> demand){
        foreach (var dst in dests){
            var lhs = Model.LinearNumExpr();
            foreach (var s in sources)
                lhs.AddTerm(1.0, ReadVar(new VariableX_Flow{ Source=s, Dest=dst }));
            var r = AddGE($"Demand@{dst}", lhs, demand[dst]); // 回傳 IRange
        }
    }
    public double Dual(IRange r) => Model.GetDual(r);
}
ModelReadVarAddLE/GE/EQSetVarLB/UB
FORM 05 · L01 建模
軟性限制式（Soft Constraints）
用懲罰取代硬約束：允許違反但加重目標式。框架依目標方向自動決定懲罰符號。須在目標式建立後呼叫。
// LHS ≤ rhs，違反時懲罰 penalty
Engine.AddLHS(1, new VariableX_WeekendCount{ Employee=e });
Engine.CreateLeSoft(rhs:4.0, penalty:0.1);

// LHS = rhs，偏差量以 delta 變數進目標式
Engine.AddLHS(1, new VariableB_ShiftAssign{ Date=d, Employee=e, Group="D" });
Engine.CreateEqSoft(rhs:demand, penalty:5.0, name:$"Demand@{d:yyyy_MM_dd}");
CreateLeSoftCreateGeSoftCreateEqSoft
FORM 06 · L03 求解
Benders 分解 / Thread 限制式
主／子問題迭代：ResetConstraint 重建、CopyModel 快照、Thread 限制式可跨 model，再用 MergeModel 併入目標 CPLEX model。
for (int it=1; it<=maxIter; it++){
    master.Solve();                       // 主問題 → LB、Y*
    var yFixed = master.GetYValues();
    sub.RebuildWithY(yFixed);             // 內部 sub.ResetConstraint()
    sub.Solve();
    UB = Math.Min(UB, fixedCost + sub.GetObjectiveValue());
    if (UB - LB <= eps) break;
    master.AddOptimalityCut(sub.Duals(), it);  // 取 dual 加 cut
}
ResetConstraintCopyModelMergeModelCreateEqualThread
FORM 07 · L02 / L03
多 Solver（CPLEX / Gurobi / 通用）
模型程式碼 solver 無關。換 solver 只換 OptEngine 與 Config，變數 / 限制式 / 目標式完全不動。
// CPLEX
var engine = new OptimFoundation.Cplex.OptEngine(new CplexConfig{ timeLimit=300 });

// Gurobi（同一份模型 code 不變）
var engine = new OptimFoundation.Gurobi.OptEngine(new GurobiConfig{ TimeLimit=300 });

engine.Build();
new VariableCreate(data, engine).Build();
new BuildModel(data, engine).Build();
engine.Solve();

FORM 09 · L02 整合
實驗與自動調參（Experiments）
把多組 Config 當 Trial 跑，統一收集 SolveMetrics（obj / gap / 時間 / node / 收斂軌跡），append 輸出 CSV + JSON。ITunableConfig 提供跨 solver 的抽象旋鈕。
var exp = new Experiment("emphasis-sweep", "比較 mipEmphasis");
foreach (var emp in new[]{0,1,2,3,4}){
    var cfg = new CplexConfig{ timeLimit=120 };
    ((ITunableConfig)cfg).Emphasis = emp;     // 抽象旋鈕
    var m = Run(cfg);                          // → EngineBase.LastMetrics
    exp.AddTrial(new Trial{ Label=$"emp={emp}", Metrics = m.LastMetrics });
}
exp.Save();   // experiments/emphasis-sweep.csv + .json

04 宣告式 Variable / Parameter 詳解

FORM 02 的展開版。把 [OptVar] / [OptParam] 加在 partial class 上，AutoSetsGenerator 在編譯期補出 set 屬性、（參數的）QTY 與建構子。你寫一行宣告，編譯後就是一個正常的 VariableBase / ParameterBase 子類別 —— 跟 FORM 01 手寫的完全等價。

前置：使用端只需 using OptimFoundation.Modeling;。attribute 由 generator 注入，不需任何額外組件參考；生成的 class 以 global::OptimFoundation.Core 全名指向基底型別。

[OptVar] — 決策變數

參數全是 index set，順序即 key 順序；變數型別由類別名前綴決定（VariableB_→Binary / VariableX_→Continuous / VariableI_→Integer，前綴非法 → compile error OPTF001）。變數不含 QTY、也不生成建構子（沿用 object initializer 寫法）。

using OptimFoundation.Modeling;

[OptVar("Date:DateTime", "Employee", "Group")]
public partial class VariableB_ShiftAssign { }

↓ 編譯期生成 VariableB_ShiftAssign.AutoSets.g.cs

// <auto-generated/>
// [VarType=Binary（由類別名前綴決定）] —— 由 AutoSetsGenerator 生成
public partial class VariableB_ShiftAssign : global::OptimFoundation.Core.VariableBase
{
    public global::System.DateTime Date { get; set; }
    public string Employee { get; set; } = string.Empty;
    public string Group { get; set; } = string.Empty;
}
命名對應：class 前綴需與 VarType 一致 —— VariableB_ ↔ Binary、VariableI_ ↔ Integer、VariableX_ ↔ Continuous。前綴是慣例（對應 BuildBVs / IVs / CVs），真正決定型別的是 attribute 裡的 VarType。

[OptParam] — 模型參數

參數沒有 VarType，全部引數都是 index set。一律生成 double QTY 值欄位，且 QTY 永遠是最後一個資料屬性；同時生成兩個建構子（params object[] 與無參）。

using OptimFoundation.Modeling;

[OptParam("Date:DateTime", "Group")]
public partial class Parameter_ShiftDemand { }

↓ 編譯期生成 Parameter_ShiftDemand.AutoSets.g.cs

// <auto-generated/>
public partial class Parameter_ShiftDemand : global::OptimFoundation.Core.ParameterBase
{
    public global::System.DateTime Date { get; set; }
    public string Group { get; set; } = string.Empty;
    public double QTY { get; set; }          // 一律生成，永遠最後

    public Parameter_ShiftDemand(params object[] sets) => InitClassBySets(sets);
    public Parameter_ShiftDemand() { }
}
QTY 規則（強制）：每個 [OptParam] 一定有 double QTY，且排在所有 set 屬性之後。框架已移除「純 key、無 QTY」的選項 —— 一個參數代表「在某組 key 下的一個數值」，QTY 就是那個數值。

Set 型別標註

set 字串格式為 "名稱" 或 "名稱:型別"；未標註型別預設 string。屬性名即 set 名稱（原樣保留大小寫）。

標註生成屬性型別範例
（省略）string（預設 = string.Empty）"Employee" → string Employee
:DateTime / :dateSystem.DateTime"Date:DateTime" → DateTime Date
:intint"MachineId:int" → int MachineId
:doubledouble"Ratio:double" → double Ratio
順序鐵則：set 引數的宣告順序 = 生成屬性順序 = 建立變數 / 傳建構參數時必須傳入的順序。順序不一致會導致 key 對不上（KeyNotFound）。參見下節「Variable Key 格式」。

手動繼承 vs 宣告式

面向手動繼承（FORM 01）宣告式（FORM 02）
變數宣告class V_X : VariableBase { …props… }[OptVar(…)] partial class V_X { }
參數 QTY手寫，需自律放最後一律補、強制最後
參數建構子手寫 params + 無參自動生成兩個
基底 using需 using …Core;global:: 全名，免 using
適用時機需自訂額外成員 / 方法時純資料 schema、零樣板

兩者可混用：宣告式產出的是 partial class，需要時在另一個同名 partial 補方法或額外屬性即可（但別重複宣告已生成的 set 屬性與 QTY）。

05 貫穿全框架的核心概念

零建構子 + 物件初始化

Variable / Parameter / Constraint 一律只宣告 properties，不寫建構子；呼叫端用 object initializer。ModelElementBase 以反射（含 PropertyInfo 快取）把值依序填入。

new VariableB_ShiftAssign{ Date=d, Employee=e, Group=g }
new Parameter_ShiftDemand{ Date=d, Group="D", QTY=5 }

Variable Key 格式

class 名 + property 值組成唯一 key；DateTime 固定 yyyy-MM-dd。property 宣告順序 = 傳入 Sets 順序，不一致就會 KeyNotFound。

VariableB_ShiftAssign@2026-01-01@E1@D

Pool 機制

送出時框架計算 (LHS項 − RHS項) {sense} (RHS常數 − LHS常數)，所以左右兩側變數可自由混用，不必手動移項。每次 Create* 後 Pool 自動清空。

抽象旋鈕（ITunableConfig）：Seed / Emphasis / FeasibilityTol / OptimalityTol / RootAlgorithm / Presolve / HeuristicEffort / MemoryLimitMb —— 各 Config 將其對映到自家欄位（CPLEX mipEmphasis ↔ Gurobi MipFocus），讓調參程式碼跨 solver 共用。
