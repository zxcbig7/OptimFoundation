教學 / Tutorial

為什麼 e => 拿得到
OptModel 裡面的 engine？

在 .AddModel(e => buildModel(data, e)) 這行裡，你從沒 new 過任何 engine，卻能在 lambda 裡直接用 e。它是哪來的？這篇用一個 FJSP 例子，把 callback（回呼委派） 的機制拆到見底。

概念 delegate / callback 形式 FORM 03 · OptModel 關鍵字 Action<OptEngine> 設計 Inversion of Control
一句話：你寫的不是「engine」，是一段「拿到 engine 之後要做什麼」的食譜。框架先 new 出唯一的 engine，再回頭一個個呼叫你的食譜、把那顆 engine 當參數餵進來。e 這名字純粹為了好讀，跟綁定無關。

前置 delegate 速成：Action<> 與 Func<>

整篇的地基是一個觀念：C# 可以把「函式」當「值」傳來傳去。裝這種值的型別叫 delegate，而 Action<> / Func<> 是 .NET 內建、最常用的兩個。

Action<>：做事、不回值（回 void）

<...> 裡填這函式吃什麼參數；Action 家族一律回 void。

Action greet = () => Log("hi");                  // 無參數、回 void
Action<string> log = s => Console.WriteLine(s);   // 吃一個 string、回 void
Action<Dataload, OptEngine> build = (d, e) => { /* 建模 */ };   // 吃兩個、回 void
型別意思
Action沒參數、回 void
Action<T>吃一個 T、回 void
Action<T1, T2>吃兩個、回 void（最多到 T16）

Func<>：要有回傳值

差別只在「回不回值」。要回值改用 Func<>，最後一個型別參數是回傳型別：

Func<bool> canSolve = () => engine.Solve();     // 無參數、回 bool
Func<int, int, bool> ge = (a, b) => a >= b;    // 吃兩 int、回 bool（最後一格 bool 是回傳型別）
要不要回值用心法
不回值（只做事）Action<...>「交出去一段動作」
有回值Func<..., TResult>最後一格是回傳型別
怎麼生出一個 Action？兩種：① lambda x => ...；② 直接給一個簽名相符的方法名（method group）——例如把 static void BuildModelA(Dataload, OptEngine) 直接當 Action<Dataload, OptEngine> 傳。FJSP 模板那六行實驗就是這樣把 BuildModelA / BuildModelB 塞進去的。

帶著這個，下一節你就會看到：.AddModel 的參數型別是 Action<OptEngine>——「吃一顆 OptEngine、回 void 的函式」，而那顆 engine 由框架執行時餵進來。

00 現場：你寫的那行

FJSP 模板裡求解一個模型的寫法。注意：整段沒有任何一處由你 new OptEngine。

using var model = new OptModel(name)
    .UseConfig(() => new CplexConfig { epGap = 1e-4, timeLimit = 60, enableLog = true })
    .AddModel(engine => buildModel(data, engine))
    .OnSolved(engine => data.WriteSolution(engine));

bool ok = model.Execute();

問題就在 .AddModel(engine => ...)：engine 從哪冒出來的、憑什麼是「模型裡那顆」？答案分三步。

01 engine 只是名字，型別由簽名決定

你不是「知道」engine 是 OptEngine，是型別系統強制的。看 AddModel 的簽名：

// OptimFoundation.Cplex / OptModel.cs
public OptModel AddModel(Action<OptEngine> build) { /* ... */ }

參數型別是 Action<OptEngine>——「一個吃 OptEngine、回傳 void 的函式」。所以你 lambda 的那個參數一定是 OptEngine，編譯器自動推斷。名字則隨你取，以下三行完全等價：

.AddModel(engine => buildModel(data, engine))
.AddModel(e => buildModel(data, e))
.AddModel(whatever => buildModel(data, whatever))
重點：「engine」不是關鍵字、也沒有任何魔法連結。它是參數名，是這段函式「將來會收到的東西」的代稱。

02 註冊 ≠ 執行：你存的是一段「之後才跑的程式」

第二個誤會最致命：以為 engine => buildModel(data, engine) 當下就執行了。沒有。此刻 engine 根本還沒有值。AddModel 只是把這段函式「收進口袋」：

// OptimFoundation.Cplex / OptModel.cs
public OptModel AddModel(Action<OptEngine> build)
{
    _modelSteps.Add(build);   // 只是把這段函式「存起來」，此刻不呼叫它
    return this;              // 回傳 this → 才能繼續 .OnSolved(...) 鏈下去
}

同理 .UseConfig、.AddVariables、.OnSolved 都只是「登記」：把你給的函式各自塞進清單。整條 fluent 鏈跑完，一次求解都還沒發生。

03 Execute() 才把 engine 綁上去

真正給 engine 值的是 Execute()。它先 new 出唯一的 engine，再回頭把你登記的函式一個個叫起來、把那顆 engine 當參數傳進去：

// OptModel.Execute()（簡化：省略計時與 log，語意不變）

public bool Execute()
{
    optEngine = new OptEngine(_configFactory());   // ① 框架自己 new 出「唯一」的 engine
    optEngine.SetModelName(_projectName);
    optEngine.Build();

    foreach (var step in _variableSteps) step(optEngine);   // ② 變數步驟先跑
    foreach (var step in _modelSteps) step(optEngine);      // ③ 模型步驟後跑 ← 你的 lambda 在這被呼叫

    _isSuccess = optEngine.Solve();                         // 求解
    foreach (var h in _solvedHandlers) h(optEngine);        // ④ OnSolved 回呼
    return _isSuccess;
}

看第 ③ 行的 step(optEngine)：step 就是你當初寫的 engine => buildModel(data, engine)，optEngine 就是框架第 ① 行 new 出來的那顆。這一刻，你 lambda 裡的 engine 才 = 框架的 optEngine。它們是同一個物件，因為框架把它當引數傳了進去——不是你去拿，是它塞給你。

04 完整時間軸

把「登記期」與「執行期」分開看，一切就清楚了。

時刻程式在做什麼engine 存在嗎？
寫下 .AddModel(e => …)把 lambda 存進 _modelSteps❌ 還沒 new
.UseConfig / .OnSolved同樣只是登記到各自清單❌
Execute() ①new OptEngine(config)✅ 誕生（在框架手上）
Execute() ②③step(optEngine) 逐一呼叫你的 lambda✅ 被當引數餵進你的 e
Execute() ④Solve() 後呼叫 OnSolved✅ 帶著解
順序保證：框架先跑完 _variableSteps 才跑 _modelSteps。所以變數一定早於約束建好——這正是為什麼變數該用 .AddVariables 登記，而不是塞進 .AddModel。

05 為什麼要這樣設計？（Inversion of Control）

你可能會問：那我自己 new OptEngine、自己照順序呼叫不就好了？可以，但那樣順序、生命週期、設定、Dispose 全要你顧。改成「你只交食譜、框架掌控時機」有幾個直接好處：

框架掌控的事

  • 依 UseConfig 建好 engine 與 solver 參數
  • 保證變數 → 約束 → 求解 → 後處理的正確順序
  • using 結束自動 Dispose，不漏 CPLEX 資源
  • 對你的具體 class 零依賴，換 solver 不用改組裝碼

你只需負責

  • 「拿到 engine 後，要建哪些變數 / 約束」
  • 「求解成功後，要拿解做什麼」
  • 其餘什麼時候發生、發生幾次，都不用管

這就是 Inversion of Control（控制反轉）：呼叫的主導權從你手上「反轉」給框架。你不呼叫框架，是框架在對的時機回呼你。

06 同一個觀念的化身

看懂一個，就看懂全部。OptModel 的三個註冊點都是同一招——收一個 Action<OptEngine>，執行期回呼：

.AddVariables(e => e.BuildBVs<VariableB_Assign>(data.Lot, data.Operation, data.Eqp))
.AddModel(e => new Constraint_NoOverlap(/* ... */, e).Build())
.OnSolved(e => data.WriteSolution(e))

連交叉實驗也是同一個心智模型——只是這次交出去的是「怎麼求解」這段動作，讓 Trial.Capture 在它量測收斂數據的前後夾著呼叫：

// () => engine.Solve() 就是「求解這件事」被包成委派交出去
var trial = Trial.Capture(engine, label, () => engine.Solve());
通則：只要看到 參數 => ... 被傳進某個方法，就對自己說：「我在交一段之後才跑的程式，那個參數的值由呼叫方在執行時決定。」

07 三個常見誤解

誤解實際
以為 e => … 當下就執行了只是被存起來；Execute() 才依序呼叫
想在 fluent 鏈之外先抓 engine 來用那時框架還沒 new engine，根本拿不到
把建變數塞進 .AddModel能跑，但語意上變數應走 .AddVariables（框架保證它早於約束步驟）
